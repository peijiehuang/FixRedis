# 修复与备份说明

## 操作边界

FixRedis 操作的目标是本机 Windows 服务 `Redis`。服务正常时不重启；仍在运行但验证失败时停止操作，不强杀进程。目标服务停止后若还存在其他 `redis-server` 进程，也会停止操作。

支持 `redis-server.exe --service-run 配置文件` 的绝对路径形式、Redis 5.0、绑定 `127.0.0.1` 的 TCP 服务及 `requirepass` 认证。密码不出现在进程参数和操作日志中。

## 备份结构

```text
%ProgramData%/FixRedis/Backups/<时间戳>-<唯一编号>/
├── originals/       原始 RDB、AOF、配置和 Redis 日志
├── manifest.json    原路径、缺失记录、大小、SHA-256
├── operation.log    本次 UTF-8 操作日志
└── work/            检查、修复使用的副本
```

访问权限限定为当前操作用户、管理员和 SYSTEM。备份复制与校验全部通过后才继续；缺少文件会记录。原数据或配置在备份后发生变化时停止应用修复。

数据目录里的 `.fixredis-quarantine-*` 是替换或隔离的旧文件。原备份和隔离文件不会自动删除，不会自动恢复历史快照。

## 全部数据丢失确认

确认框显示故障原因和备份位置，默认选择“否，保留数据并退出”。

- **拒绝**：不继续清空。若尚未应用 AOF 截断，原数据保持不变；若已应用截断后启动仍失败，则保留截断产物及原始备份。
- **接受**：隔离当前 RDB/AOF；AOF 模式创建有效空 AOF。保持原配置，尝试启动一次并验证。

生产环境需由负责人确认可接受的数据损失。程序不会根据文件大小、备份成功或服务能否启动来判断业务数据可以丢弃。

## 常见问题

### 修改或删除 dump.rdb 为什么不影响 Redis？

Redis 运行时使用内存数据，不会因编辑磁盘快照立刻改变内存。重启加载哪个文件由真实配置决定：启用 AOF 时优先加载 AOF；RDB 路径由 `dir` 和 `dbfilename` 决定。RDB 缺失可以空库启动；未满足保存条件时也不会立即重新生成文件。

### 为什么检查器通过，启动仍可能失败？

AOF 检查器主要验证格式和完整性，不能穷尽命令语义。未知命令可能通过检查但阻止启动；某些错误参数会让 Windows Redis 5 崩溃，只留下通用崩溃日志。证据不足时工具保留数据并报告失败，不猜测清空。

### “恢复成功”是否代表数据完整？

不是。成功只表示服务 Running、实例身份和配置匹配、认证后的 PING 通过、loading=0 及持久化状态正常。业务数据完整性需另行核验。截断字节数不会换算成数据条数。
